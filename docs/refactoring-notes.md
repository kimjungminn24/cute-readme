# 리팩토링 노트 (2026-08)

"성능 향상 + 오픈소스답게 깔끔한 코드, 단 오버엔지니어링 금지"라는 목표로 진행한
리팩토링의 **판단 과정**을 남긴다. 무엇을 했는지보다 **왜 그렇게 정했는지, 무엇을 일부러
안 했는지**가 이 문서의 목적이다.

> 이 노트를 쓴 뒤 GitHub 활동 연동(`src/activity.js`, `src/decorate.js`)은 제거됐다.
> 아래에서 그 두 파일을 다루는 대목은 당시 기록으로 그대로 남긴다.

## 1. 전제 점검: "성능"의 방향부터 다시 정했다

처음 목표는 막연히 "성능 향상"이었지만, 코드를 읽고 나서 방향을 바꿨다.

- 이 프로젝트는 CI에서 **하루 한 번 실행되고 끝나는 배치 렌더러**다. 전체 실행이
  수십 ms 수준이라 런타임 속도는 병목이 아니다.
- 이 프로젝트의 진짜 성능 지표는 **출력 SVG 바이트 수**(README 로딩)인데, 이건 이미
  최적화되어 있었다:
  - `toMarkup()`: 가로 런 + 세로 병합(2차원 RLE) 후 색상별 path 하나로 합침
  - `shader()`: 문자열 파싱하는 `shade()`를 픽셀마다 부르지 않도록 명도별 캐싱
  - `hash()`: `Math.random` 대신 좌표 해시 → 같은 입력이면 항상 같은 SVG (결정적 렌더링)

**결론: 속도 최적화는 하지 않는다.** 후보로 봐둔 것(아래 §5)은 프로파일링해서 숫자가
나올 때만 한다. 측정 없는 최적화가 이 목표에서 말한 오버엔지니어링의 전형이다.

## 2. 안전망 먼저: 스냅샷(특성화) 테스트

리팩토링의 정의는 "동작을 바꾸지 않는 것"인데 기존 테스트는 부분 속성만 검증했다.
그래서 손대기 전에 `test/snapshot.test.js`를 추가했다:

- `renderRoom`(데모 방 + 벽 무늬 7종 + 견본), `renderGuestbook`(테마 11종 + 빈 방명록)의
  **SVG 전문을 바이트 단위로** `test/fixtures/snapshots.json`과 비교한다.
- 렌더링이 결정적(위 `hash()` 덕분)이라 스냅샷이 흔들리지 않는다. 이 코드베이스만의
  공짜 이점.
- 그림을 의도적으로 바꿨다면 `UPDATE_SNAPSHOTS=1 npm test`로 픽스처를 다시 굽는다.

이후 모든 변경은 이 스냅샷이 그대로인 것으로 "동작 보존"을 증명했다.

## 3. 네이밍: 전부 풀지 않고 세 종류만 골라 고쳤다

픽셀과 기하 코드에서 `x, y, c, r, u, d` 같은 수식 변수는 짧은 게 관례고 더 읽기 쉽다.
"클린코드 = 무조건 긴 이름"이 아니라서, 문제가 되는 세 패턴만 고쳤다.

| 전 | 후 | 이유 |
|---|---|---|
| `g` (픽셀 Map) | `dots` | `g`가 pixel.js에선 희소 픽셀 Map, room.js에선 geometry 객체다. **같은 이름이 두 의미**로 쓰여 새 기여자가 가장 헷갈릴 지점 |
| `g` (geometry) | `geo` | 〃 |
| `tex()` | `speckle()` | 공개 API의 축약어. "texture"보다 실제 역할(얼룩 질감)이 드러나는 이름 |
| `TW2` / `TH2` | `TILE_HALF_W` / `TILE_HALF_H` | 화면 타일 절반 크기라는 뜻이 이름에 없었다 |
| `PTW2` / `PTH2` | `DOT_TILE_HALF_W` / `DOT_TILE_HALF_H` | 위와 같고, 도트 공간(1도트 = 2px)이라는 구분을 이름에 실었다 |
| `pts()` (room.js) | `pointsAttr()` | 반환값이 SVG `points` 속성 문자열이라는 걸 드러냄 |
| `pxBox(g, fc, fr, …)` | `pxBox(dots, footprintCols, footprintRows, …)` | 시그니처는 풀어 쓰고, 함수 안 수식에서만 `fc/fr`로 별칭. 공개 표면은 자기설명적으로, 수식은 짧게 |

주의한 것: catalog.js의 스프라이트 팔레트에는 **문자 키 `g`**(초록 계열)가 있어서
일괄 치환이 위험했다. 호출 패턴별 치환 후 `\bg\b` 잔여 검색으로 SVG `<g>` 태그와
팔레트 키만 남았음을 확인했다.

덤: `WALL_H_PX`는 정의만 있고 아무도 안 쓰는 죽은 코드라 삭제.

## 4. 구조: 두 가지만 했고, 한 가지는 하려다 접었다

### 한 것 ① guestbook 테마 데이터 분리

guestbook.js 587줄 중 440줄이 `THEMES` 데이터였다. `guestbook-themes.js`로 빼서:

- 렌더링 로직 파일이 ~150줄이 됐다.
- 오픈소스에서 가장 흔할 PR("새 테마 추가")이 **로직 파일을 건드리지 않게** 됐다.
- 기존 임포트 경로가 깨지지 않도록 `DEFAULT_THEME`, `GUESTBOOK_THEMES`는 guestbook.js에서
  재수출한다.
- 카드 치수 상수(`PAD`, `HEADER` 등)는 테마의 frame/underlay와 본문 배치가 같은 좌표 위에서
  만나야 해서 테마 파일 쪽에 두고 내보냈다.

### 한 것 ② clampGrid 중복 제거

그리드 크기 제한(4~12)이 room.js `geometry()`와 decorate.js `clamp()`에 **복붙**되어
있었다. 최대 크기를 바꾸는 날 한쪽만 고치면 조용히 어긋나는 전형적 DRY 위반.
`clampGrid()`를 room.js에서 export하고 decorate.js가 가져다 쓰게 통합했다.
(의존 방향: decorate → room → catalog, 순환 없음)

### 안 한 것: DEMO_ROOM 분리

DEMO_ROOM도 데이터라 분리 후보였지만 접었다. 빼내면 `DEFAULT_THEME`(room.js 내부 상수)를
가져와야 해서 **room ↔ demo-room 순환 임포트**가 생기거나 색상값을 복붙해야 한다.
30줄짜리 데이터를 위해 순환이나 중복을 만드는 건 손해. 이런 게 "분리는 무조건 선"이
아닌 이유다.

### 반쯤 한 것: activity.js vs github.js

둘 다 GitHub을 호출해서 파일명만으로 역할 구분이 안 됐다. 파일명 변경은 스크립트와 워크플로
임포트를 전부 흔들어서, 각 파일 머리에 경계 주석(컨트리뷰션/언어 ↔ 이슈 댓글/아바타)을
다는 것으로 갈음했다. 파일명 변경의 이득 < 임포트 경로 churn 비용.

## 5. 함수형 프로그래밍: "하지 않기로" 한 결정

"함수형으로 바꾸면 너무 축약돼서 못 알아볼 것"이라는 걱정이 있었는데, 그건 함수형의
본체가 아니라 **포인트프리/커링이라는 표기법**에 대한 걱정이다. 함수형의 본체
(순수성, 부수효과 격리)는 이미 이 코드에 들어 있다:

- `decorate()`가 입력을 `structuredClone` 후 새 객체 반환: 불변성
- 좌표 해시 노이즈: 참조 투명성 (같은 입력 → 항상 같은 출력)
- 렌더 함수 전부가 `(데이터) → SVG 문자열` 순수 함수

`fillPoly`와 `toMarkup` 안에서 Map을 mutate하는 건 함수 밖에서 관측 불가능한 **지역
변이**라 함수형 관점에서도 문제없고, 이 도메인(픽셀 채우기)에선 그게 더 빠르고 읽기
쉽다. **결론: 지금 스타일(순수 함수 + 명시적 루프) 유지. Ramda식 축약 도입 금지.**

## 6. 미뤄둔 것 (하려면 측정부터)

- **픽셀 Map의 문자열 키**: `"x,y"` 키는 픽셀마다 문자열 생성 + `toMarkup`에서 재파싱
  비용이 있다. 정수 키(`(y + OFFSET) * STRIDE + x`)로 바꾸면 상수 계수가 줄지만,
  `node --cpu-prof scripts/preview-room.js`로 쟀을 때 상위에 뜰 때만 한다.
  전체 실행이 수십 ms인 프로그램에서 이건 취미지 개선이 아니다.
- **주석 언어**: 주석 품질은 좋다(값의 이유, 방식의 이유를 적는 주석). 다만 전부
  한국어라, 글로벌 기여자를 받으려면 어떤 네이밍 개선보다 주석 영어화가 더 큰 접근성
  개선이다. 한국어 커뮤니티 타깃이면 지금이 강점. 프로젝트 방향의 문제라 보류.
  (추기: 공개 준비하며 결정했다. 주석은 전부 영어로 옮겼고, 한글 렌더링을 검증하는
  테스트 데이터와 README 번역판만 한국어로 남겼다.)

# 2차 리팩토링 노트 (2026-08-21)

"1000줄 넘는 파일이 있다"는 걱정에서 출발해 Fowler『리팩터링 2판』 3장(코드에서 나는
악취)과 6장(기본적인 리팩터링) 기준으로 다시 훑은 기록. 1차와 같은 목표를 유지한다.
**깔끔하게, 단 오버엔지니어링 금지.**

## 1. 표적부터 다시 정했다: 파일 길이는 냄새가 아니다

의심한 곳은 `src/catalog.js`(2244줄)와 `editor/editor.js`(1734줄)였지만, 재보니 둘 다
아니었다.

| 파일 | 줄 | 최상위 선언 | 최장 함수 | 판정 |
|---|---|---|---|---|
| `catalog.js` | 2244 | 142 | `personArt` 106줄 | 나머지는 전부 스프라이트 **데이터 표**라 냄새 아님 |
| `editor.js` | 1734 | 136 | 83줄 (평균 12.7) | **이미 잘 분해돼 있음**, 긴 함수 없음 |

정작 긴 함수는 578줄과 626줄짜리 "작은" 파일 안에 있었다.

- `renderSuika` **178줄** (suika.js)
- `renderRepoCard` **132줄** (repocard.js)

3장이 말하는 냄새는 **길이가 아니라 책임**이다. 파일 크기로 표적을 고르면 데이터 표를
쪼개느라 시간을 쓰고 진짜 긴 함수는 그대로 남는다.

## 2. 안전망 먼저 (1차와 같은 순서)

1차 스냅샷은 `renderRoom`, `renderGuestbook`, `personArt`만 덮고 있었다. 손대려는 두
렌더러는 **특성화 테스트가 없어서** 픽스처부터 늘렸다.

- 테마 전부 / 빈 목록 / 1명(통이 납작해져 `minH` 보정이 걸리는 경로) / 아바타 유무 /
  `drop`, `names`, `links` 끄기 / 폭 클램프 양끝 / 없는 테마명
- `npm test` 302 → 330

그리고 코드를 고친 뒤 **픽스처를 다시 굽지 않고** 통과하는 것으로 무변경을 증명했다.

## 3. 함수 추출하기(6.1)만으로는 부족했다. 매개변수 객체(6.8)가 짝이다

두 함수 다 단계가 10개 안팎인데, 단계들이 지역변수를 잔뜩 공유한다
(`W, H, jarH, jl, jr, jb, il, ir, ib, dy, cr, id …`). 이걸 그대로 함수로 빼면 인자가
열 개씩 붙어서 **긴 매개변수 목록**으로 냄새만 바꿔치기하게 된다.

그래서 순서를 이렇게 잡았다.

1. 계산부를 `suikaLayout()` / `repoCardLayout()`으로 먼저 추출. 순수 함수, 결과는
   레이아웃 객체 `L`
2. 그리기 함수는 `L` 하나(+`opts`)만 받아 **SVG 조각 배열**을 돌려준다
3. 쌓는 순서는 `renderSuika` / `renderRepoCard` 한 곳에만 남긴다

결과:

| 함수 | 전 | 후 |
|---|---|---|
| `renderSuika` | 178줄 | **29줄** |
| `renderRepoCard` | 132줄 | **23줄** |

두 파일 모두 60줄 넘는 함수가 없어졌다(남은 건 데이터 표와 물리 헬퍼 `roll` 56줄).

### 추출선은 이미 그어져 있었다

3.3절의 *"주석을 달만한 부분은 무조건 함수로 만든다"* 가 그대로 들어맞았다. 원래 코드에
`// 통. 위가 열린 U자다`, `// 유리 반사. 알 위에 얹혀야…`, `// 아래 줄: 언어 → 스타 →
포크` 같은 주석이 블록마다 붙어 있었고 **그 위치가 곧 경계**였다. 주석은 지우지 않고 각
함수의 문서로 옮겼다. 값의 이유를 적은 주석이라 버릴 게 아니었다.

### repocard: `textWriter` 분리가 핵심이었다

`drawn`/`textW`/`write` 세 클로저가 `dots`와 `font`를 붙잡은 채 함수 중간에 떠 있었다.
이걸 `textWriter(theme, dots)` 한 곳으로 모으니 **"글자를 도트로 찍을까 `<text>`로
찍을까"라는 판단이 한 군데**로 들어갔고, 나머지 층은 `text.write(...)`만 부르면 된다.

## 4. 도트 글꼴 경로: 무테스트 구멍을 메웠다

`test/repocard.test.js`에 `dots`가 **한 번도 나오지 않는다.** 즉 도트로 찍는 분기는
원래부터 아무도 안 보고 있었다. 리팩토링 대상 한복판이라 그냥 넘길 수 없었다.

1. `git show HEAD:src/repocard.js`로 원본을 꺼내 리팩토링본과 **같은 프로세스에서
   나란히 렌더** → 테마 7종 × 2 + 분기 8개 = **22/22 바이트 동일**
2. 이 대조를 일회성 스크립트로 버리지 않고 **스냅샷 8개로 굳혔다**

`dot`을 켠 테마가 `pixel` 하나뿐이라 케이스가 싸게 먹혔다. 못 그리는 글자(`漢字`, `🙂`)가
섞여 그 줄만 통째로 `<text>`로 떨어지는 분기도 포함했다.

## 5. 일부러 안 한 것

### `editor.js` 분리: 미룸

냄새가 없는 건 아니다. 긴 함수가 아니라 **분산된 변경(Divergent Change)** 이다. Room /
Photo / Suika / README / Cards 탭이 한 파일에 있어서 "사진 기능 수정"과 "방명록 테마
수정"이 같은 파일을 건드린다. 게다가 조건도 좋다. `<script type="module">`로 실려서
ESM 분리에 빌드 도구가 필요 없고, `/* ---------- 사진 ---------- */` 같은 **경계 주석이
이미 그어져 있다.**

그런데도 미뤘다. **테스트가 없어서 "바이트 단위로 같다"를 증명할 방법이 없다.** 검증이
브라우저에서 탭마다 눌러보는 수작업이 되는데, 그건 이번 회차의 다른 변경들과 안전성
등급이 다르다. 손으로 확인할 수 있는 자리에서 따로 한다.

### `catalog.js` 데이터 분리: 우선순위 낮음

1차의 `guestbook-themes.js` 분리와 논리는 같다("새 스프라이트 추가" PR이 로직 파일을
안 건드리게). 다만 그건 리팩토링이라기보다 **파일 이동**이고, `catalog.js`의 로직은
`personArt` 하나뿐이라 지금 급하지 않다.

### 줄 수가 늘어난 것: 정상이다

`suika.js` 578 → 639, `repocard.js` 626 → 702. 함수 경계와 문서가 붙어서다. 추출
리팩토링은 원래 **줄 수를 늘리고 복잡도를 줄인다.** 줄 수가 줄기를 기대했다면 표적이
틀린 것이다.

## 6. 긴 파일은 긴 함수와 다른 문제다. 여기서부터는 모듈 이동

1~3에서 함수는 짧아졌는데 파일은 오히려 길어졌다(578→639, 626→702). "찾아다니기
힘들다"는 문제는 함수 추출로 안 풀린다. 그건 **모듈 이동**의 몫이다. 기준은 1차의
guestbook-themes 분리와 같다. **가장 흔할 PR이 로직 파일을 안 건드리게.**

### catalog.js 2244줄 → 배럴 13줄 + 구역 6개

함수 241줄 / 데이터 1999줄로 89%가 스프라이트 표였다. 자르기 전에 구역 사이 참조부터
쟀더니 실제 의존은 **벽이 OAK/OAK_DARK 두 색을 쓰는 것 하나뿐**이었다. `skills→fx`는
CSS 클래스 문자열 `'fx-bob'`, `person→legs`는 매개변수 이름이라 둘 다 오탐이었다.
문자열과 주석을 안 걷어내고 이름만 세면 없는 의존이 보인다.

| 파일 | 줄 | 내용 |
|---|---|---|
| `catalog-base.js` | 39 | 좌표 헬퍼 + 기본 재질 색 |
| `catalog-floor.js` | 857 | 바닥 오브젝트 + `FLOOR_ITEMS` |
| `catalog-wall.js` | 171 | 벽걸이 + `WALL_ITEMS` |
| `catalog-effects.js` | 81 | `EFFECTS` |

| `catalog-person.js` | 964 | 캐릭터 전부 |
| `catalog.js` | 13 | 배럴 |

**배럴을 둔 이유**: room.js와 editor.js, 테스트가 쓰던 `'./catalog.js'` 경로를 하나도 안
건드리려고. 1차에서 activity.js/github.js 이름 변경을 접은 것과 같은 계산이다. 임포트
경로 churn 비용이 이득보다 크다.

**base를 배럴에서 뺀 이유**: `off`/`P`/`legs`는 원래 모듈 지역 상수였다. 파일을 가르느라
export로 승격했지만 배럴로까지 흘리면 **원래 없던 공개 표면**이 생긴다. 구역 파일끼리만 쓴다.

### repocard.js 702줄 → 346줄 + repocard-themes.js 371줄

테마 표 225줄과 무늬 도형을 갈랐다. 이 파일은 **import가 하나도 없다.** 무늬가 전부
문자열을 짓는 순수 함수라 새 테마를 넣을 때 렌더러를 읽을 일이 없다.

**`ICONS`는 일부러 안 옮겼다.** `bookIcon`/`star`/`forkIcon`을 부르는데 그건 렌더러 쪽에
있어서, 같이 옮기면 두 파일이 서로를 import하는 순환이 된다. 1차에서 DEMO_ROOM 분리를
접은 것과 같은 이유다. 기존 경로가 안 깨지도록 `REPO_CARD_THEMES`와
`DEFAULT_REPO_CARD_THEME`는 repocard.js에서 다시 내보낸다.

### 안 가른 것

- **suika.js 638줄**: 함수가 497줄이다. 데이터가 `SUIKA_THEMES` 46줄뿐이라 갈라도 남는 게 없다.
- **room.js 832줄**: 함수 465 / 데이터 355. 스타일 표를 빼면 660줄쯤 되는데 이득이 catalog만큼 뚜렷하지 않다.
- **catalog-person.js 964줄**: 스프라이트와 스타일 표가 번갈아 나와 자를 자리가 깔끔하지 않다. 2244줄에서 내려온 것으로 일단 둔다.

### 파일 가르기는 스냅샷으로 부족하다

렌더 결과만 보는 스냅샷은 "export를 하나 흘렸다"를 못 잡는다. 실제로 첫 시도에서 배럴이
base 헬퍼 9개를 덧붙여 내보냈고 스냅샷은 전부 통과했다. 그래서 원본 모듈과 가른 뒤
모듈을 **같은 프로세스에서 나란히 불러 export를 통째로 대조**했다. 함수는 소스 텍스트까지
비교했다. 줄을 그대로 옮긴 리팩토링이라 같아야 맞다.

- catalog: export 28개 목록과 값 전부 일치, `personArt` 90종 렌더 바이트 동일
- repocard: export 8개 목록과 값 전부 일치

## 2. 안전망은 2차의 교훈을 도구로 만들었다

"파일 가르기는 스냅샷으로 부족하다(export를 흘려도 통과한다)"를 이번엔
스크립트로 박았다. export 표면(이름, 값, 함수 소스 길이)을 가르기 전후로
통째 대조하고, editor.js와 scripts가 부르는 임포트 114개를 전수 확인했다.

그 도구가 2차 노트의 함정을 그대로 밟았다가 고쳐졌다.

- 주석 속 이름을 의존으로 오인 (moving 구역의 "furnace의 불과 같은" 주석)
- 템플릿 리터럴을 통째로 지워 ${shell(geo, theme)} 같은 보간 속 호출 4건을 놓침
- 정규식 리터럴의 따옴표를 문자열 시작으로 읽어 살아 있는 idsIn을 죽었다고 봄

"문자열과 주석을 안 걷어내고 이름만 세면 없는 의존이 보인다"는 사람 얘기가
아니라 도구 얘기이기도 했다.

### 추기 (2026-08-31): editor.js를 뷰별로 갈랐다

위에서 "안 갈랐다"고 적은 그 파일이다. 전제였던 "검증이 수작업"이 바뀌어서다.

그 그물 위에서 1,192줄을 갈랐다. 척추는 editor-shared.js다. 방 상태(app.state)와
